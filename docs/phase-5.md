# Phase 5 顶级规划文档

## 阶段定位

在第四阶段已经完成「可探索、可表达、可互动」的基础上，第五阶段聚焦 **"可发布、可访问、可持续维护"**。

核心命题：让 Plate. 从一个已经具备完整体验的个人博客作品，进入 **正式上线前的收口阶段** —— 完成部署闭环、性能优化、SEO 补全、内容验收与稳定性加固，确保它不仅“能看”，而且“能发”。

## 阶段目标

1. **发布闭环完成**：前后端运行方式、环境变量、部署流程、域名/协议准备清晰可执行。
2. **上线质量达标**：SEO、404、RSS、导航、移动端、后台配置等关键路径稳定可用。
3. **性能与体验优化**：压缩高成本资源，降低首屏压力，避免过重动画影响真实访问体验。
4. **内容收口完成**：移除占位内容，补全页面信息，让首页、About、Now、Photography、Fragments、Wall 都达到可展示状态。
5. **发布前验收标准建立**：形成一个明确的 checklist，后续每次发布可复用。

## 范围（In Scope）

### 模块 A：部署与运行闭环
- 确定发布架构（静态页面 + Node API）
- 环境变量与密钥策略梳理
- 本地开发 / 生产部署差异收口
- 域名、HTTPS、公开访问路径检查

### 模块 B：SEO 与可发现性完善
- 页面 meta/OG/description 收口
- sitemap / robots / canonical 策略
- RSS、404、站内链接完整性检查
- 搜索引擎与分享预览准备

### 模块 C：性能与体验优化
- 图片资源尺寸与体积优化
- JS / CSS 加载策略检查
- 动画降级与移动端体验校正
- 首屏体验、交互阻塞与滚动性能优化

### 模块 D：内容与展示收口
- 首页 Hero / Featured / About 文案打磨
- About / Now / Photography / Fragments / Wall 内容补齐
- 删除模板占位项与不一致文案
- 后台配置内容可直接驱动前台展示

### 模块 E：发布前验收与文档
- 发布清单（Launch Checklist）
- 常见问题与回滚策略
- 开发日志持续记录
- 部署文档与环境变量文档补全

## 非范围（Out of Scope）

- 再新增大型互动模块
- 引入前端框架重构（React/Vue 等）
- 评论系统重构或账号体系升级
- CI/CD 自动化平台接入
- 多语言系统、主题切换、后台权限分级

## 任务拆解（WBS）

## 模块 A：部署与运行闭环

### A1 统一前后端请求策略

**目标**：消除开发环境与生产环境 API 路径不一致的问题，确保 AI、文章、配置、碎片、照片、Wall 等功能在部署后可稳定工作。

**重点任务**：
- 检查 `assets/js/config.js`、`ai-assistant.js` 等请求入口
- 区分开发地址与生产地址，避免硬编码 `localhost`
- 若继续使用 Express，则明确静态资源与 API 是否同域部署
- 补充部署说明中的 API 路径规则

**验收标准**：
- [ ] 本地开发可访问
- [ ] 生产部署不依赖 `localhost`
- [ ] 所有 fetch 路径策略一致

---

### A2 环境变量与密钥收口

**目标**：让管理员令牌、AI Key、站点 URL、模型与 API URL 都有明确的配置来源和说明。

**重点任务**：
- 统一 `.env.example` 与后台「API 配置」面板能力
- 明确环境变量优先级与配置文件回退逻辑
- 检查 `data/secrets.json` 的忽略策略是否正确
- 保证无密钥时提示可理解、可恢复

**验收标准**：
- [ ] `.env.example` 完整
- [ ] `data/secrets.json` 不进入版本库
- [ ] 后台配置能覆盖 AI 使用所需参数

---

### A3 部署文档闭环

**目标**：让项目具备可复制的部署步骤，自己和别人都能按文档上线。

**重点任务**：
- 更新 `docs/deployment.md`
- 写清：安装依赖、启动前端、启动 API、环境变量、上线方式
- 明确推荐部署平台或推荐发布结构

**验收标准**：
- [x] 新机器按文档可跑通
- [x] 部署步骤不依赖口头说明

---

## 模块 B：SEO 与可发现性完善

### B1 页面级 SEO 收口

**目标**：确保首页、文章页、About、Now、Photography、Fragments、Graph、Wall 都具备合理的 title / description / OG 信息。

**重点任务**：
- 检查所有 HTML 的 `<title>` 和 `<meta name="description">`
- 统一 Open Graph / 社交分享信息
- 检查文章页是否按文章内容生成对应 SEO 信息
- 修复明显错误（如重复符号、占位文案、描述不完整）

**验收标准**：
- [ ] 每个主要页面都有独立 title/description
- [ ] 无明显占位 SEO 文案
- [ ] 分享卡片具备基础可读性

---

### B2 索引控制与站点地图

**目标**：明确哪些页面应该被索引，哪些不该被索引，并补全 sitemap / robots。

**重点任务**：
- 检查 `editor.html`、404、测试页等是否 `noindex`
- 新增或完善 `robots.txt`
- 新增或生成 `sitemap.xml`
- 检查 RSS 是否与站点 URL 一致

**验收标准**：
- [x] 后台页不被索引
- [x] 公开页面可进入 sitemap
- [x] robots 与 sitemap 不冲突

---

### B3 站内链接与可发现性检查

**目标**：避免孤立页面和错误导航，让用户与搜索引擎都能完整走通站点。

**重点任务**：
- 检查 navbar、footer、404、archive、graph、wall、fragments 的互链
- 检查随机漫游、图谱跳转、文章跳转是否闭环
- 检查死链与空链接

**验收标准**：
- [ ] 无主要页面孤立
- [ ] 无明显死链
- [ ] 404 页面具备有效回流路径

---

## 模块 C：性能与体验优化

### C1 图片与静态资源优化

**目标**：降低图片和装饰资源对加载速度的影响。

**重点任务**：
- 检查摄影图片、上传图片、封面图大小
- 压缩过大的资源，必要时生成更适合网页展示的尺寸
- 检查是否存在未使用的大资源或重复资源

**验收标准**：
- [ ] 首屏不被超大图拖慢
- [ ] 图片资源尺寸合理
- [ ] 无明显冗余静态资源

---

### C2 动画与滚动性能优化

**目标**：保留品牌感的前提下，避免动画过多影响实际使用。

**重点任务**：
- 检查 GSAP / ScrollTrigger / Lenis 在各页面的使用密度
- 优化移动端动画强度
- 对非关键动画做延迟、降级或按视口触发
- 检查 AI 助手、Wall、Graph 页面交互性能

**验收标准**：
- [ ] 页面切换与滚动顺滑
- [ ] 移动端无明显掉帧
- [ ] 动画不阻塞主要功能

---

### C3 基础可访问性与易用性

**目标**：保证网站不是只“好看”，也能正常使用。

**重点任务**：
- 检查按钮、输入框、链接的可点击性与对比度
- 补全必要的 `aria`、`alt`、focus 状态
- 检查键盘可用性（尤其 AI 助手与后台）
- 检查移动端输入体验与弹窗体验

**验收标准**：
- [ ] 关键按钮有明确 hover/focus 状态
- [ ] 图片有 alt
- [ ] 主要表单可键盘操作

---

## 模块 D：内容与展示收口

### D1 首页与核心页面文案收口

**目标**：让用户进入网站第一眼就能理解你是谁、你做什么、你擅长什么。

**重点任务**：
- 打磨首页 Hero、About、Featured Projects 文案
- 统一中英文语气与品牌表达
- 检查 About / Now 页面是否有信息断层
- 检查页脚、按钮、导航命名一致性

**验收标准**：
- [ ] 首页信息密度合理
- [ ] 核心页面语言风格统一
- [ ] 不存在模板残留文案

---

### D2 内容完整度验收

**目标**：发布前确保站点不是“有页面没内容”。

**重点任务**：
- 检查文章数量与代表性
- 检查摄影分类是否有足够内容
- 检查 Fragments / Wall 是否需要初始展示内容
- 检查空状态文案是否自然

**验收标准**：
- [ ] 主要内容页不空
- [ ] 空状态设计合理
- [ ] 首页链接过去的页面都值得展示

---

### D3 后台驱动能力验收

**目标**：让发布后的日常维护尽量通过后台完成，而不是频繁改代码。

**重点任务**：
- 检查文章、碎片、照片、AI 配置、站点模板配置是否可用
- 检查新增内容后前台刷新是否正常
- 检查配置修改是否能真正反映到页面

**验收标准**：
- [ ] 常用内容更新不依赖手改文件
- [ ] 后台操作路径清晰
- [ ] 错误提示能帮助恢复

---

## 模块 E：发布前验收与文档

### E1 发布清单（Launch Checklist）

**目标**：形成一个可以在每次发布前执行的标准清单。

**建议清单项**：

- RSS / robots / sitemap 正常
- 404 页面正常
- 移动端检查完成
- 死链检查完成

---

### E2 文档与日志延续

**目标**：让项目未来继续迭代时有历史可查。

**重点任务**：
- 持续维护 `docs/devlog.md`
- 更新 `docs/README.md` 里的阶段说明
- 补充 Phase 5 完成后的总结文档（如需要）

**验收标准**：
- [ ] 本阶段有独立文档
- [ ] 开发日志持续记录
- [ ] 文档目录能反映当前真实阶段

## 开发顺序建议

| 优先级 | 模块 | 理由 |
|--------|------|------|
| 1 | A1+A2 部署与配置闭环 | 不先打通上线链路，后续优化无法真正验证 |
| 2 | B1+B2 SEO 与索引控制 | 发布前最容易遗漏，但影响长期发现性 |
| 3 | D1+D2 内容收口 | 决定网站发布时的观感与完整度 |
| 4 | C1+C2 性能优化 | 在内容和功能都定型后做更高效 |
| 5 | E1+E2 发布清单与文档 | 作为上线前最终收口 |

---

## 设计约束（所有模块必须遵守）

1. **不新增大型系统**：第五阶段以收口和优化为主，不再引入新的重型功能模块。
2. **保持品牌统一**：继续沿用 Klein Blue、玻璃拟态、衬线标题与无衬线正文体系。
3. **优先稳定而非炫技**：任何优化若影响可用性，应优先保证稳定上线。
4. **继续原生技术栈**：不引入前端框架，维持当前 HTML / CSS / JS + Express 架构。
5. **发布优先**：凡是不能直接提高“可发布性”的工作，优先级都应降低。
6. **文档同步更新**：本阶段每完成一个关键模块，必须同步更新开发日志与相关部署文档。

## 阶段完成定义（Definition of Done）

当以下条件全部满足时，第五阶段可视为完成：

- [ ] 本地开发与生产部署链路都已跑通
- [ ] 所有公开页面具备基本 SEO 信息
- [ ] AI 助手、后台、照片、碎片、Wall 等功能在生产路径下可用
- [ ] 无明显占位内容、空白关键页面或主要死链
- [ ] 已完成一次完整的发布前检查清单
- [ ] 文档（部署、开发日志、阶段规划）已同步更新
